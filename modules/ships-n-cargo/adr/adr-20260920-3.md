# ADR: Return expected use-case outcomes as explicit results

**Date:** 2026-09-20

## 1. Context

Ships and Cargo currently communicates every unsuccessful use-case outcome by throwing an error.
[ADR-20260920-2](adr-20260920-2.md) classifies those errors by
semantic kind and distinguishes expected domain outcomes from infrastructure failures, invariant
violations, and unknown failures. The application boundary catches all of them and maps them to the
HTTP response policy.

Some thrown errors are ordinary alternatives in a use-case contract. A requested ship may not
exist, a supplied value may be invalid, or the current aggregate state may reject an operation.
Other thrown errors mean that the application could not execute normally or that an assumption was
violated. Those two groups require different control flow even though JavaScript represents both
with exceptions.

The error taxonomy is also being refined so that expected errors share an `ExpectedError` base,
with `DomainError` and `ApplicationError` identifying ownership beneath it.

## 2. Problem

**Expected outcomes are absent from use-case signatures.** A `Promise<void>` signature does not tell
a caller that a use case can fail because a ship is missing or because a domain rule rejects the
operation. The caller learns the contract from implementation details, tests, or a broad `catch`.

**One exception channel mixes normal alternatives with execution failures.** Controllers must catch
expected outcomes, managed infrastructure failures, invariant violations, and unknown thrown values
through the same mechanism before applying different policies.

**Broad catches weaken exhaustiveness.** Adding an expected use-case outcome does not require a
caller or mapper to handle it. It can silently fall through to generic exception handling.

## 3. Decision

### Use cases return expected outcomes explicitly

Every use-case method will return a `Result<Success, Failure>` value. `Failure` will enumerate the
expected errors declared by that use case, and every member will extend `ExpectedError`.

The repository will own a small discriminated `Result` type rather than add a runtime dependency.
Its success and failure variants will be distinguishable through a literal discriminant so callers
can narrow them exhaustively.

For a use case without a success payload, `Success` will be `void`. A missing ship will therefore be
a failure value such as `Result<void, ShipNotFound>`, not a thrown exception.

### The application boundary converts expected domain rejections

Domain behavior may continue to enforce its own rules with `DomainError` exceptions internally.
The use-case boundary will catch only `ExpectedError` values that are part of its declared failure
union and return them as failed results. It will not convert arbitrary thrown values into results.

An expected error omitted from a use case's declared failure union is an incomplete contract and
must fail static verification rather than being accepted through a broad cast.

### Exceptional failures continue to throw

`InfrastructureError`, `InvariantError`, and unrecognized thrown values will remain exceptional.
Use cases will not turn them into failed results. They will propagate to the outer boundary, where
they receive logging and the existing opaque server-error response.

This preserves exception stacks and causes for failures that interrupt normal execution while
keeping expected alternatives visible in method signatures.

### Inbound adapters handle results before exceptions

An inbound adapter will inspect the returned `Result` and map a declared expected failure to its
transport response. Its exception handler will deal only with infrastructure, invariant, and
unknown failures.

Transport status codes and response disclosure remain adapter policy. Neither the `Result` type nor
concrete expected errors will carry HTTP status codes.

### The migration changes all use-case contracts coherently

All existing use cases, their controllers, and their tests will migrate together. The completed
codebase will not leave some expected use-case outcomes returned and others thrown merely because
they belong to different operations.

**This changes every use-case calling contract and requires coordinated updates to controllers,
tests, and any direct callers.** The stronger signatures are the intended benefit, but the migration
is not source-compatible.

## 4. Consequences

Callers will be able to discover expected failures from types and handle them without using
exceptions for ordinary control flow. Exception handling at the HTTP boundary will become narrower,
and new expected outcomes will require deliberate mapping.

The application layer will contain conversion logic where domain methods still throw expected
domain errors. That logic must remain narrow so programming defects and dependency failures are not
misreported as ordinary outcomes.

`ExpectedError` remains useful after the migration. It marks the only error family eligible for a
failed result and provides a runtime guard at boundaries that translate existing domain exceptions.

## 5. Alternatives considered

* **Continue throwing every failure.** Rejected: expected outcomes remain invisible in use-case
  signatures and share control flow with infrastructure failures and defects.
* **Return every failure, including infrastructure and invariant errors.** Rejected: callers could
  treat interrupted execution and programming defects as normal business alternatives, and every
  signature would acquire failures it cannot meaningfully resolve.
* **Adopt a third-party Result library immediately.** Deferred: the required discriminated union is
  small, and no library-specific composition behavior has yet justified a dependency.
* **Migrate only `ShipNotFound` to a result.** Rejected: controllers would need two mechanisms for
  expected outcomes, and method signatures would communicate the contract inconsistently.

## 6. Limits accepted

This decision does not eliminate exceptions inside the domain model, prescribe a functional
programming library, or make infrastructure failures recoverable. It does not define retry policy,
logging infrastructure, or a public error response schema.

The decision governs use-case boundaries. It does not require every private helper to return a
`Result`, and it does not treat every error that can be anticipated by developers as an expected
caller outcome.

## 7. Conclusion

Ships and Cargo will return every expected use-case outcome through an explicit, typed `Result` and
reserve thrown exceptions at that boundary for infrastructure failures, invariant violations, and
unknown failures. This makes expected alternatives part of each use-case contract, but it does not
remove domain exceptions or provide recovery for exceptional execution failures.
