# ADR: Establish the foundational ship domain model

**Date:** 2026-09-23

## 1. Context

Ships and Cargo is a fictitious domain model used to demonstrate domain-driven design, CQRS, and
event sourcing. Its write model centers on one event-sourced `Ship` aggregate. The aggregate can be
created, moved between a port and the sea, and have cargo loaded or unloaded.

The current model begins a created ship at a synthetic missing port. It also represents being at sea
as a special port, permits arrival from any initialized state, and permits cargo operations without
regard to the ship's location. Cargo is identified by its description, and it carries a derived
`hasBeenInCanada` flag that governs no business behavior.

Domain events carry `occurredAt` and `recordedAt`. Most command APIs accept an optional generic
timestamp that becomes `occurredAt`; omitting it causes the server to supply the current time.
Consequently, the same command can mean either "perform this operation now" or "record an operation
that happened at a caller-selected time." Aggregate stream position already supplies the ordering
used to reconstruct state.

## 2. Problem

**The aggregate admits states that have no domain meaning.** A missing port is treated as a ship
location, while at sea is represented as a port without a country. These sentinel values allow
invalid concepts to flow through otherwise valid `Port` APIs.

**The lifecycle does not protect physical transitions.** A ship can arrive while already at a port,
which moves it directly between ports, and cargo can be loaded or unloaded while it is at sea.
Registration does not establish the location needed for a clean operating cycle.

**Cargo description is being used as identity.** Two distinct cargo units cannot share a name, and
different operations do not apply the same case-sensitivity rule. The model cannot reliably refer to
one physical unit throughout its onboard lifecycle.

**Unused historical state obscures the aggregate's purpose.** The Canada flag is maintained during
arrival replay, but no decision consumes it. Keeping derived state without a governing rule makes
the aggregate appear to enforce behavior that does not exist.

**History can be changed or incompletely replayed.** Events and aggregate properties expose mutable
state, the in-memory journal retains object references, and replay silently ignores unknown event
types. A caller can alter recorded facts, and an incomplete event model can still produce a state
that appears authoritative.

**Timestamp ownership is ambiguous.** A normal command can supply the time placed on the resulting
domain event. This mixes immediate commands with reports of externally observed facts and gives a
generic timestamp several incompatible meanings.

## 3. Decision

### Ships are registered at a known port

`RegisterShip` replaces `CreateShip`. Registration requires a real initial port and produces a
registration event containing that port. Before registration, the ship aggregate is absent; it is
not represented by a ship with sentinel identifiers or a missing location.

### Ship location is a closed domain state

The location of a registered ship is exactly one of `AtPort`, containing a real `Port`, or `AtSea`.
`Port` represents only a real port and therefore always has a real country. Missing-port,
no-country, and at-sea port values are removed.

The aggregate enforces the cycle `AtPort -> AtSea -> AtPort`. Departure is valid only from
`AtPort`. Arrival is valid only from `AtSea`. An arrival cannot be used to initialize a ship or move
it directly from one port to another.

### Onboard units are containers with stable identity

`Container` replaces the current cargo concept. Every container has a stable `containerId` and a
description. Identity comparisons use only `containerId`; descriptions do not determine equality or
uniqueness. Distinct containers may have the same description.

Loading and unloading are valid only while the ship is `AtPort`. Loading an already onboard
container and unloading a container that is not onboard remain rejected outcomes. The aggregate
does not distinguish containers by letter case in their descriptions because descriptions are not
identifiers.

The Canada flag and its arrival handling are removed. Historical or compliance attributes will be
introduced only when a concrete decision consumes them.

### Domain history is immutable and replay is strict

Domain events, event payload values, aggregate state exposed outside the aggregate, and journaled
history are immutable. Journal adapters must not allow retained or returned object references to
change stored history.

Replay accepts only the closed set of events understood by the aggregate. It rejects unknown event
types, events whose aggregate identifier differs from the stream being reconstructed, duplicate
registration, and event sequences that violate the location or container lifecycle. It does not
silently produce state from a partial or impossible history.

### Normal commands use server-owned event times

Normal ship command APIs do not accept `occurredAt`, `recordedAt`, or a generic timestamp override.
The server supplies `occurredAt` when the aggregate accepts the command and the local domain
transition occurs. The server also supplies `recordedAt` in association with recording the event.
Clients control neither value.

Aggregate stream position is authoritative for replay order. Timestamps do not reorder an aggregate
stream. Planned future times, such as a scheduled departure or estimated arrival, must be modeled as
explicitly named domain values rather than future occurrence times.

A delayed fact produced by another system is a different interaction. If the model later consumes
such facts, a dedicated reporting command or inbound integration contract must preserve the source
event identity, source identity, original occurrence time, and local receipt or recording time. It
must also define idempotent redelivery and source-specific timestamp validation. This capability is
not part of normal ship commands.

## 4. Consequences

The aggregate will have a small, explicit state machine with no synthetic ports. Registration,
movement, and container handling will use one vocabulary, and every accepted command will preserve
the physical lifecycle represented by that vocabulary.

Stable container identity permits multiple similarly described containers and gives load and unload
operations one comparison rule. Removing unused Canada tracking reduces state and replay behavior
without removing an active business rule.

Strict replay will fail visibly when history cannot be interpreted completely. This prevents an
apparently valid aggregate from being reconstructed from unknown or impossible facts.

**The foundation change crosses every application layer.** Commands, events, serializers, use cases,
HTTP contracts, persistence tests, and aggregate tests must change together. The work will be split
into ordered, independently verified implementation items rather than one broad change.

**Strict immutability may require defensive copying or immutable representations at adapter
boundaries.** TypeScript `readonly` declarations alone do not prevent mutation of runtime objects.

Removing caller-selected times makes normal command handling unambiguous. It also means the normal
HTTP API cannot backdate a domain transition. A future requirement to ingest delayed observations
will require a distinct contract rather than restoring a generic timestamp parameter.

## 5. Alternatives considered

* **Keep `CreateShip` and initialize it with a real port.** Rejected: registration better describes
  adding a known ship to this system, while creation implies constructing the physical vessel.
* **Retain missing and at-sea values as special ports.** Rejected: neither value is a port, and both
  weaken the invariants of `Port` for the convenience of aggregate state representation.
* **Continue identifying cargo by its name.** Rejected: a description is neither unique nor stable
  identity for a physical shipping unit.
* **Keep the Canada flag as an example of derived state.** Rejected: state without a decision that
  consumes it adds machinery without demonstrating a domain invariant.
* **Ignore unknown events for forward compatibility.** Rejected: replaying without applying every
  relevant fact can yield incorrect state that appears complete.
* **Keep an optional caller timestamp on normal commands.** Rejected: it conflates immediate intent,
  delayed observation, clock skew, and future planning under one field.
* **Model delayed external observations now.** Deferred. It becomes worthwhile when an actual source,
  delivery contract, idempotency key, and conflict policy can be defined.

## 6. Limits accepted

This decision does not model voyage planning, diversion, detailed port calls, berths, container
weight, vessel capacity, dangerous goods, customs, or container loss.

`Ship` remains the sole aggregate root in this foundation. `Port` is an immutable value object, and
`Container` is a child entity used to enforce the consistency of one ship's onboard manifest. This
model does not own a container's global equipment lifecycle or prevent the same container identifier
from appearing in another ship aggregate. Voyage and Shipment are not modeled.

If later rules require one authoritative container location, independently managed voyage schedules,
port operations, or commercial shipment lifecycles, those concepts should be evaluated as separate
aggregate roots. Coordination between them would use domain events and explicit process logic rather
than one enlarged transaction.

Strict replay detects histories the model cannot interpret; it does not repair corrupted data.
Server-owned timestamps establish ownership and meaning, but they do not provide globally ordered
time across aggregate streams.

## 7. Conclusion

Ships and Cargo will use a registered ship at a known port, a closed at-port or at-sea location,
stably identified containers, immutable strict history, and server-owned event timestamps as its
domain foundation.
