# ADR: Store domain events in explicit versioned envelopes

**Date:** 2026-09-27

## 1. Context

Ships and Cargo stores each domain event as JSON text behind the application event-journal port.
The `EventJournal` contract exposes aggregate stream version separately from event payloads. The
PostgreSQL journal persists stream position in its `version` column, while the in-memory journal
derives it from the number of events in the stream. Both journals serialize events whose payloads
carry the event type, aggregate identifier, timestamps, and event-specific values. Serialization
also prevents retained object references from changing in-memory history.

The event payload handler currently selects a serializer by event type. Individual serializers
produce and parse complete JSON documents. Their event-specific shapes are inconsistent: port
values are represented as pairs of flat fields, while containers are represented as nested values.
The journal adapters currently select serializers directly. The PostgreSQL adapter additionally
parses stored JSON to discover the event type before delegation.

There is no deployed development or production journal and therefore no retained legacy payload
format to preserve. This permits the repository to establish its initial durable format explicitly.

## 2. Problem

**Aggregate stream version does not describe payload schema.** Stream position orders one
aggregate's events and protects optimistic concurrency. It cannot also identify which representation
of an event type was stored.

**The stored payload has no explicit schema contract.** A future reader cannot distinguish an
original representation from a later one. Treating a missing version as version one would preserve
an accidental unversioned format and encourage new projects to discover versioning only after data
exists.

**Serialization responsibilities are distributed across storage adapters and event serializers.**
An adapter must understand enough JSON to choose a serializer, and every serializer repeats common
envelope construction. A new journal adapter could reproduce those assumptions differently.

**The event-specific representation lacks one consistent boundary.** Common metadata and domain
data share one flat object, and value objects do not follow one structural convention. This makes a
future schema transformation broader than the event-specific data it intends to change.

## 3. Decision

### Every stored event uses a required version-one envelope

The initial stored representation of every event will use this envelope:

```json
{
  "type": "ShipRegistered",
  "schemaVersion": 1,
  "aggregateId": "abc",
  "occurredAt": "2024-01-02T03:04:05.000Z",
  "recordedAt": "2024-01-03T04:05:06.000Z",
  "data": {
    "name": "King Roy",
    "port": {
      "name": "Kingston",
      "country": "US"
    }
  }
}
```

`schemaVersion` is a positive integer scoped to one event type. It is distinct from the aggregate
stream version in the `EventJournal` contract. Every payload must contain `schemaVersion`. A
missing version is invalid and will not default to version one.

The envelope fields `type`, `schemaVersion`, `aggregateId`, `occurredAt`, `recordedAt`, and `data`
are required. Timestamps remain ISO 8601 strings and retain their existing meanings.

### Event-specific data uses nested domain value shapes

The `data` object contains only the values particular to that event. Ports use `{ "name",
"country" }`, containers use `{ "containerId", "cargoReference", "description" }`, and events
containing several ports name each nested value by its role, such as `origin`, `destination`, or
`previousDestination`. An event with no event-specific values uses an empty `data` object.

This structure is the first published schema. The existing flat fields are replaced directly; they
are not designated as a historical version and receive no upcaster.

### One codec owns envelope serialization and deserialization

The event payload handler will expose complete serialize and deserialize operations. It will own JSON
parsing, envelope construction and validation, event-type lookup, schema-version routing, and
upcaster execution. Event serializers will describe their event type and current schema version,
convert a domain event to event-specific data, and construct a domain event from validated metadata
and current event-specific data.

Journal adapters will pass domain events to the codec when appending and pass opaque stored payloads
to the codec when reading. They will not parse event types or schema versions themselves. The
application `EventJournal` port and journal storage layout remain unchanged.

The domain event exposes facts and timestamps, but it does not define the stored JSON envelope. The
codec constructs common metadata from those event properties.

### Deserialization rejects payloads it cannot interpret completely

The codec will reject malformed JSON, a malformed envelope, an unknown event type, a missing or
invalid schema version, a stored version newer than the registered serializer, and an incomplete
upcaster chain. It will not guess a schema or partially reconstruct an event.

Errors that occur while interpreting stored history remain distinct from journal availability
failures. Reading bytes successfully from storage does not make an uninterpretable payload an
infrastructure outage.

### Future schema changes use consecutive read-time upcasters

The codec will support an ordered chain of upcasters registered for one event type. Each upcaster
advances exactly one adjacent schema version, such as version one to version two. It transforms only
event-specific `data`; the codec preserves the envelope's event type, aggregate identifier, and
timestamps.

Upcasters must be pure and deterministic. They do not read current databases, call external
services, consult the clock, or invent facts that were not present in the stored event. When a
required current value cannot be truthfully derived, the model must represent the historical
unknown, introduce a different event, or make a separately justified data-migration decision.

Upcasting occurs in memory during reads. The journal is not rewritten. New events are serialized
only at the current registered schema version; the codec does not downcast.

### The generic mechanism is tested without fictional production history

No production event registers an upcaster while every event remains at schema version one. Generic
chain selection, consecutive transformation, and failure behavior will be tested with test-only
schemas and serializers. A production upcaster is added only when a production event representation
actually advances.

### Deployments introduce new writes only after compatible readers

Upcasting lets a new reader consume older representations. It does not let an old reader consume a
newer representation. A project using rolling deployments must make all active readers compatible
before new-version writes begin, or use a coordinated deployment that prevents old readers from
encountering those writes. The repository will document this reader-first constraint as part of the
recipe.

## 4. Consequences

Every persisted event identifies its representation explicitly from the first published schema.
Storage adapters share one codec and remain concerned with stream mechanics rather than event JSON.
Nested event data provides a stable boundary for later transformations, and a future schema change
has an explicit extension point with fail-closed behavior.

**Every existing serializer and its fixtures change together.** There is no retained data to
migrate, but the initial conversion touches all event types and both journal adapters. Exact payload
fixtures become part of the public storage contract and should change only through a deliberate
schema-version decision.

**The generic upcaster mechanism exists before a production event consumes it.** This cost is
accepted because the repository is a reference implementation and the mechanism can be verified
without mislabeling an existing event representation as historical.

**New payload versions constrain deployment order.** Teams cannot assume that an upcaster provides
bidirectional compatibility. A writer switch must account for older application instances that may
still read the same journal.

Journal storage continues to retain serialized JSON without enforcing envelope fields or nested
data shapes; application validation and compatibility tests carry that responsibility.

## 5. Alternatives considered

* **Treat absent `schemaVersion` as version one.** Rejected: no retained payload requires this
  compatibility rule, and it would establish an accidental unversioned format as the baseline.
* **Keep event-specific fields flat beside envelope metadata.** Rejected: it preserves inconsistent
  value-object representations and gives future upcasters a less distinct transformation boundary.
* **Store `schemaVersion` as journal metadata outside the payload.** Rejected: a self-describing
  payload keeps each event type's representation version with its data and works consistently across
  journal adapters.
* **Add a real `ShipRegistered` version-one to version-two upcaster now.** Rejected: there is no
  retained version-one representation to preserve. The canonical nested envelope is version one.
* **Wait to build any version-aware mechanism until an event changes.** Rejected for this reference
  implementation: projects following the recipe should establish explicit versions before their
  first durable event rather than retrofit them afterward.
* **Rewrite old journal rows whenever a schema changes.** Rejected: rewriting facts increases
  migration risk and weakens the journal's append-only history. A separately justified migration
  remains possible when read-time transformation cannot meet a concrete requirement.

## 6. Limits accepted

This decision versions serialized event representations. It does not version aggregate stream
positions, domain behavior, HTTP contracts, or database DDL. Those concepts evolve under their own
contracts.

The envelope does not add global event identity, global ordering, command idempotency, an outbox, or
projection delivery. It does not make the journal queryable by event fields or validate JSON at the
database boundary.

Generic upcaster tests prove routing and transformation mechanics, not the correctness of a future
production transformation. Each real upcaster must still justify that its output preserves the
meaning of the recorded fact.

Reader-first deployment guidance does not implement a deployment coordinator or feature flag. A
production system must choose a rollout mechanism appropriate to its topology.

## 7. Conclusion

Ships and Cargo will store every domain event in a required, explicitly versioned envelope whose
nested `data` object is interpreted by one centralized codec. The codec will support strict,
consecutive read-time upcasting, but no production upcaster will exist until an event schema truly
advances. This establishes a recipe for future compatibility without claiming legacy history or
changing the event-journal contract.
