# ADR: Use PostgreSQL for the Ships and Cargo journal with optimistic concurrency

**Date:** 2026-09-21

## 1. Context

Ships and Cargo currently stores domain events in an in-memory journal. Its application use cases
depend on `src/application/ports/event-journal.ts`, and the composition root selects the journal
implementation. The journal reads all events for one aggregate and appends one or more events. It
does not expose a stream version. Use cases read, replay, decide, and append in separate calls.

The existing event serializers write `recordedAt` into JSON but reconstruct events with a new
`recordedAt` value. A persistent journal would expose that loss whenever it reads an event back.

[ADR-20260920-2](adr-20260920-2.md) separates expected outcomes, infrastructure failures, and
invariants. [ADR-20260920-3](adr-20260920-3.md) requires use cases to return expected outcomes in
typed results while exceptional failures continue to throw. A durable adapter and concurrent writes
must respect those contracts.

The repository has one bounded context today. More modules may introduce other bounded contexts.
The deployment target and local PostgreSQL runtime have not been selected.

## 2. Problem

**The default journal loses events on process restart.** It demonstrates replay but cannot show that
the same application port works with durable relational storage.

**The present port cannot reject stale decisions.** Two requests can replay the same stream, make
decisions from the same state, and both append. Merely assigning each append a new version would
allow a stale decision to enter the journal.

**Deserialization changes event history.** Reconstructed `recordedAt` values describe read time
instead of the original recording time.

**Database setup can fail late.** Constructing a connection pool does not prove that the database,
schema, or expected constraint exists. A missing setup step should fail before the HTTP server
accepts requests.

**A storage namespace should express bounded-context ownership.** An environment name such as
`dev` changes meaning across deployments; a shared `event_store` schema would obscure which context
owns a table when more contexts are added.

## 3. Decision

### Each bounded context owns a stable PostgreSQL schema

The Ships and Cargo table will be `ships_n_cargo.event_journal`. The schema name will be the same
in local, test, and production databases. SQL will qualify the schema explicitly rather than rely
on `search_path`.

An initial deployment may place several bounded-context schemas in one PostgreSQL database. Each
context will own its SQL and connection configuration. It must not rely on cross-schema joins,
foreign keys, or transactions with another context. A later move to a separate database can retain
the `ships_n_cargo` schema and journal SQL, but still requires data migration and deployment cutover.

### PostgreSQL stores ordered, append-only aggregate streams

The initial schema will contain one journal table with `event_id`, `aggregate_id`, `version`, and
`event_payload`. A unique `(aggregate_id, version)` constraint will protect each stream position;
`event_id` remains the primary key and a storage identifier. The stream begins at version zero
before any event, and persisted events receive successive positive versions. Reads will explicitly
order by version.
The payload remains serialized JSON text so that the journal need not interpret event fields beyond
the event type needed for deserialization.

The PostgreSQL adapter will independently implement the application port. It will use `pg` and
parameterized, direct SQL. No ORM or runtime migration framework will be introduced for the initial
table.

### Journal writes require the version used to make the decision

The port will return both events and the current version when reading an aggregate. Its append
operation will identify one aggregate, require the version the caller read, and accept events only
for that aggregate. A multi-event append will assign consecutive versions and commit atomically.
The in-memory adapter will implement the same version contract so application behavior does not
depend on the selected adapter.

The PostgreSQL adapter will check that the stored stream is at the expected version and will rely
on the unique stream-position constraint to reject a concurrent writer at the same next version.
It will translate only that specific version race into a typed journal version conflict. Connection
and other recognized driver failures will continue to use the journal infrastructure error.

### Use cases reconsider commands after version conflicts

A use case that receives a journal version conflict will reread the stream, replay it, and rerun
the business decision from the original command inputs. It will then attempt a new append if the
command remains valid. Retries will be bounded. A domain rule that becomes false will return its
specific expected failure; contention that remains after the retry bound will return a declared
application conflict. Controllers will map that expected conflict through the existing result
handling policy. Infrastructure failures and invariant violations will still propagate as
exceptions.

The adapter will distinguish the stream-position constraint from other unique constraints. It
will not classify every database uniqueness failure as a retryable version race.

### Persisted events preserve their original timestamps

Every registered serializer will retain both `occurredAt` and `recordedAt` through a JSON round
trip. This fix will precede the PostgreSQL adapter. No historical journal data exists to migrate.

### Setup and startup are separate operations

The in-memory journal remains the default. PostgreSQL is selected explicitly and configured by a
connection string. A `db:setup` command will apply the checked-in initial SQL to an existing
PostgreSQL database. It will succeed when the schema already matches and report an incompatible
existing schema rather than silently accept it. Database provisioning remains the deployment
owner's responsibility.

When PostgreSQL is selected, startup will connect and verify the required schema, table shape,
and stream-position constraint before the Express server listens. A missing or incompatible setup
will stop startup with an actionable error. Normal server startup will not issue schema-changing
SQL or fall back to memory. Later database outages remain runtime journal failures.

### Tests prove both contracts and database behavior

Unit tests will cover serializer round trips, version conflicts, bounded command retries, error
classification, and startup validation. Database-backed tests will cover ordered replay, persistence
across journal instances, atomic multi-event writes, and competing appends against PostgreSQL.
The CI test path will run those tests and preserve the existing overall coverage baseline, with an
explicit coverage gate rather than relying on coverage reporting alone.

## 4. Consequences

The application can select memory or PostgreSQL at composition time. Events survive process
restarts in PostgreSQL, and a version conflict prevents a command based on stale state from being
silently appended. The initial database setup and server startup each have a clear responsibility.

**The version-aware port changes every use case and both journal adapters.** Controllers and tests
must handle the new declared contention outcome. This work is larger than replacing one constructor
in the composition root.

**A shared database remains a shared operational boundary.** Context schemas can have distinct
roles and names, but they share database availability, capacity, and recovery operations. Moving
one context later requires a data cutover even when its SQL stays the same.

**Durable storage adds operational work.** PostgreSQL must be provisioned, backed up, monitored,
and upgraded by the deployment owner. The first-run command and startup check reduce setup errors;
they do not operate the database.

## 5. Alternatives considered

* **Keep only the in-memory journal.** Rejected: it cannot demonstrate durable replay or relational
  enforcement of concurrent stream writes.
* **Use environment-named schemas.** Rejected: schema names would vary for the same context and
  require environment-specific SQL or search paths.
* **Use `public` for every context.** Rejected for the initial shared database: context-owned
  schemas keep table names and privileges separate without relying on a search path.
* **Put every context in one `event_store` schema.** Rejected: the namespace would express storage
  technology rather than ownership and would encourage a shared journal table.
* **Place each context in a separate database now.** Deferred. The context-owned schema and
  per-context connection configuration leave this option open when isolation or scaling requires it.
  Multiple databases can still share one PostgreSQL deployment, so the shared database is an
  organizational choice rather than a required cost saving.
* **Keep the current append signature and calculate the next version inside the adapter.**
  Rejected: both writers could succeed after making decisions from the same old state.
* **Use serializable transactions for every command.** Deferred. They would require retrying the
  whole read and decision transaction, while the explicit version contract also works with the
  in-memory adapter and other storage technologies.
* **Add an ORM or migration framework now.** Rejected: the initial schema and queries are small,
  and no schema evolution yet justifies those dependencies.
* **Use Postgres.js for the adapter.** Deferred. Its SQL API fits, but an
  [open transaction reservation issue](https://github.com/porsager/postgres/issues/1189) makes
  `pg` the selected driver for atomic journal appends at the time of this decision.
* **Make a local container runtime the required database path.** Deferred. A local container recipe
  using OCI images may improve developer convenience, but the runtime contract is a connection
  to an existing PostgreSQL database.

## 6. Limits accepted

This decision establishes the write-side journal and its concurrency behavior. It does not add a
query projection, a committed global event feed, snapshots, cross-context transactions, or a
complete CQRS read side. Per-aggregate versions do not provide global commit order. A future
projection mechanism must make an explicit delivery and ordering decision.

Expected-version checks do not resolve an ambiguous acknowledgement after a successful commit.
Stable command or event identity and idempotency require a separate decision before claiming
exactly-once command behavior. Event payload format evolution also remains separate from table
schema evolution.

The initial `db:setup` command handles the first schema only. A later DDL change will require a
versioned migration decision. This ADR does not choose a local container tool, production
packaging, a managed database provider, or a deployment orchestrator.

## 7. Conclusion

Ships and Cargo will use a context-owned PostgreSQL journal with direct SQL and an expected-version
append contract. The same contract will govern the in-memory adapter, and use cases will reconsider
commands after concurrent writes. This provides durable aggregate replay and safe write-side
concurrency; it does not complete the CQRS read side or the operational design of a production
database deployment.
