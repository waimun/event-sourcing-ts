# ADR: Use aggregate stream position as PostgreSQL journal row identity

**Date:** 2026-09-21

## 1. Context

[ADR-20260921](adr-20260921.md) § "PostgreSQL stores ordered, append-only aggregate
streams" chose an `event_id` primary key and a separate unique constraint on
`(aggregate_id, version)`. The journal port, however, identifies a stream by aggregate ID and
returns its current version. It does not expose an independent event identifier.

Every stored event already has one unique position within its aggregate stream. The aggregate ID
selects the stream, and the positive version selects one event in that stream. Reads use those same
values to retrieve an aggregate's events in order, and appends use the next version to reject a
stale decision.

This ADR supersedes only the row-identity and constraint choice in ADR-20260921. Its decisions about
the context-owned schema, direct SQL, expected-version writes, retry behavior, setup validation,
and database-backed tests remain active.

## 2. Problem

**The surrogate event ID has no current runtime contract.** The application does not create, read,
return, or reference `event_id`. A generated bigint would identify a database row without
identifying anything used by the journal port or domain model.

**Two indexes would enforce one useful identity plus one unused identity.** A primary key on
`event_id` and a unique constraint on `(aggregate_id, version)` both add write and storage cost, but
only the stream-position index supports replay and optimistic concurrency.

**Adding a UUID would imply semantics that have not been chosen.** A durable event identity could
support idempotency, external references, or a global event feed. None of those behaviors exists in
the current journal contract, and ADR-20260921 deliberately left stable event identity and a
committed global feed for later decisions.

## 3. Decision

### Aggregate stream position is the journal row identity

The PostgreSQL journal table will contain `aggregate_id`, `version`, and `event_payload`. Its primary
key will be `(aggregate_id, version)`. The aggregate ID alone cannot be a key because one aggregate
has many events; the version distinguishes each event in that stream.

The initial table will not contain `event_id`. The composite primary key replaces both the proposed
surrogate primary key and the separate unique stream-position constraint.

### The primary-key constraint detects concurrent stream writes

The primary-key constraint will have one stable, explicit name. The PostgreSQL adapter will
translate a uniqueness violation into a journal version conflict only when PostgreSQL identifies
that exact constraint. Other uniqueness violations and driver failures remain infrastructure
failures.

Reads will continue to select one aggregate and order by version. The primary-key index begins with
`aggregate_id` and then `version`, matching that access path.

### Independent event identity remains deferred

The journal will not generate a bigint, UUIDv7, or other independent event ID. A future feature that
needs events to be addressed outside their aggregate stream must first define the identity's scope,
generation boundary, serialization contract, and idempotency behavior. That decision may add a
column through a migration without changing the meaning of the composite stream-position key.

### The initial schema is corrected before deployment

The PostgreSQL journal schema has not been merged or deployed, so adopting the composite key changes
the initial setup SQL rather than migrating stored production events. Schema verification and
database-backed tests will require the composite primary key and reject the superseded table shape.

## 4. Consequences

The relational key now expresses the invariant the application already uses: an event occupies one
version in one aggregate stream. The same named constraint both identifies a row and arbitrates
competing appends. The table avoids an unused column, identity sequence, and index.

**A composite key is wider than a bigint foreign key.** Any future table that references a journal
row by relational foreign key would carry both aggregate ID and version. No such table exists. A
future global feed or projection mechanism must separately define event identity, commit ordering,
checkpointing, and delivery, including whether they require journal columns or separate
infrastructure.

The schema provides no standalone event identifier and no global ordering. Sequence allocation
would not have guaranteed commit order in any case. Per-aggregate replay and optimistic concurrency
remain unchanged.

## 5. Alternatives considered

* **Keep a generated bigint primary key.** Rejected: no current application or storage behavior
  consumes it, while the stream-position constraint still carries the useful invariant.
* **Store an application-generated UUIDv7 event ID.** Deferred. It becomes worthwhile when a
  concrete consumer needs stable event identity, idempotency, or external event references and can
  define their semantics.
* **Use only `aggregate_id` as the primary key.** Rejected: every aggregate stream contains multiple
  events, so aggregate ID alone is not unique.
* **Leave the table without a primary key.** Rejected: the database should enforce that one stream
  position contains at most one event, and the adapter needs the named constraint to classify a
  concurrent append precisely.

## 6. Limits accepted

This decision does not introduce global event identity, global commit order, an outbox, projection
delivery, or command idempotency. It does not define how a later migration would populate an event
ID for existing rows. Those concerns require consumers and failure semantics that the current
write-side journal does not have.

The composite key prevents duplicate stream positions. It does not by itself prove that versions
are gapless when SQL is written outside the journal adapter; the adapter remains responsible for
assigning consecutive versions in one atomic append.

## 7. Conclusion

Ships and Cargo will identify each PostgreSQL journal row by `(aggregate_id, version)` and use that
composite primary key as the exact optimistic-concurrency constraint. It will not carry an unused
surrogate event ID. Independent event identity remains a future decision rather than an implied
property of the initial schema.
