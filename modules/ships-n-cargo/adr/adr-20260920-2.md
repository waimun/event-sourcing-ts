# ADR: Classify failures with a typed error kernel

**Date:** 2026-09-20

## 1. Context

Ships and Cargo currently defines `ApplicationError` and `InvalidArgumentError` in
`src/shared/error.ts`. Value-object validation errors, missing aggregates, business-rule
conflicts, and invalid aggregate states all inherit from `InvalidArgumentError`. Application
controllers consequently translate every recognized error into HTTP 400 and every other thrown
value into a generic HTTP 500 response.

Several failures bypass that shared mechanism. Event serializer registration, serializer lookup,
and in-memory journal preconditions throw native `Error` subclasses. Four use cases also define
separate `ShipNotFound` classes whose only meaningful difference is operation-specific message
text.

The in-memory event journal is the current persistence adapter. It is expected to be replaceable
by a relational database adapter without changing the application or domain behavior that depends
on the journal interface.

## 2. Problem

**One base class collapses distinct outcomes.** Invalid client input, a missing ship, a conflicting
state transition, and an impossible internal state require different application behavior. Treating
all of them as invalid arguments loses that distinction and produces inaccurate HTTP statuses.

**Messages act as both identity and presentation.** Operation-specific prose distinguishes otherwise
duplicated errors, while no stable code exists for tests, logging, or boundary decisions. Changing
wording can therefore change behavior accidentally if a consumer begins to inspect it.

**Failure handling is duplicated at the boundary.** Each controller repeats the same recognition,
status selection, logging, and fallback response. This makes it easy for endpoints to disagree and
forces domain classes to inherit from a transport-driven category.

**Persistence replacement needs a stable failure contract.** A relational adapter will introduce
managed technical failures that the in-memory adapter does not naturally produce. Those failures
must be distinguishable from caller errors and programming defects without making one adapter
inherit from another.

**Unclassified errors can silently bypass the taxonomy.** Native error subclasses currently coexist
with the shared mechanism. Without an automated constraint, new bare errors can reintroduce the same
ambiguity after migration.

## 3. Decision

### Every recognized failure belongs to a typed kernel

All intentionally modeled failures will extend a common `BaseError`. The base type will carry a
mandatory `domain`, a stable `code`, a semantic `kind`, read-only structured `meta`, and an optional
`cause`. Its message is a developer-readable label or an explicitly safe expected-outcome message;
no component may parse the message to identify the failure.

The initial domain type contains the literal `ships-n-cargo`. Domain ownership remains mandatory
even while the repository contains only one bounded context. New bounded contexts must extend the
domain type and identify their concrete errors explicitly.

Error codes are stable uppercase identifiers. Metadata carries values such as aggregate identifiers,
field names, or operations. Metadata is diagnostic data and is not automatically public response
content.

### Failure categories describe semantics rather than source directories

`DomainError` represents expected outcomes caused by a caller request or current business state. Its
allowed kinds are `validation`, `not-found`, and `conflict`.

`InfrastructureError` represents managed technical failures in adapters or external dependencies.
Its initial kind is `fatal`. A technical failure may be retryable by an operator or later request,
but it is not an expected business outcome.

`InvariantError` represents an assumption that should be impossible when the application and domain
are correct. Its kind is always `invariant`. It remains a programming failure and must not be caught
inside business logic as a recoverable result.

The directory containing a throw does not determine its category. A persistence adapter can detect
an invariant violation, and an application use case can report an expected domain outcome.

### Existing failures receive explicit classifications

Required values, invalid identifiers, invalid names, invalid dates, invalid countries, and invalid
dock command inputs are validation errors.

A missing ship and missing cargo are not-found errors. The operation-specific `ShipNotFound` classes
will become one error with one stable code and operation-neutral identity.

An existing ship identifier, already-loaded cargo, and a departure attempted from an invalid current
state are conflict errors.

Aggregate identifier mismatches, impossible aggregate lifecycle states, missing or mismatched event
serializers, and an append operation with no events are invariant errors. In particular, the current
in-memory journal's `EventIsRequired` condition is programmer misuse of the journal contract, not a
technical persistence outage.

### The application boundary owns transport mapping

Error classes will not carry HTTP status codes. A shared application-boundary mapper will translate
semantic kinds consistently:

| Kind | HTTP status |
|---|---:|
| `validation` | 400 |
| `not-found` | 404 |
| `conflict` | 409 |
| `fatal` | 500 |
| `invariant` | 500 |

Expected domain outcomes may return their safe message through the existing response envelope.
Infrastructure errors, invariant errors, and unrecognized thrown values return the same opaque 500
message. Their codes, metadata, causes, and stacks remain available for server-side diagnostics and
must not be copied automatically into the response.

The stable code is part of the internal error contract. Adding it to the public HTTP response is a
separate API-contract decision.

### Persistence adapters share an error contract, not an implementation hierarchy

The typed kernel will define an event-journal infrastructure failure with a stable code such as
`EVENT_JOURNAL_UNAVAILABLE`. It records the attempted operation and retains the original failure as
its cause.

The in-memory and future relational journals will independently implement the existing journal
interface. A relational adapter will catch expected driver or connection failures and translate them
into the journal infrastructure error. It will not inherit from the in-memory implementation.

The in-memory adapter will not add artificial failure paths or broad exception wrapping merely to
throw the infrastructure error. Boundary tests will exercise the behavior with a journal test double
that rejects with the shared error. This establishes the future adapter contract without pretending
that ordinary `Map` operations expose database-style outages.

### Production code rejects new bare errors after migration

After existing modeled failures have moved to the kernel, an automated architecture guard will fail
verification when production source introduces a bare native error throw or a custom error outside
the kernel hierarchy. Tests may continue to use native errors as fixtures for unexpected-failure
behavior.

The guard supports the taxonomy; it does not make third-party exceptions recognized. Unknown thrown
values still reach the application boundary and receive opaque 500 handling.

## 4. Consequences

Controllers will share one status and disclosure policy. Tests can assert stable codes and semantic
categories without coupling behavior to message wording. Missing resources and business conflicts
will no longer be reported as generic invalid arguments.

Future persistence adapters can translate technical failures without changing domain errors or HTTP
controllers. Invariant failures remain visible for diagnosis while staying behaviorally distinct from
recoverable business outcomes.

**The migration touches every existing custom error and every controller error path.** The change must
update unit tests and endpoint expectations together to avoid a partially classified system.

**Stable codes and domain names become compatibility commitments.** Renaming either requires deliberate
review even when the public HTTP response does not expose them.

**Structured metadata creates a disclosure obligation.** Logging and future response formats must
review metadata fields rather than assuming they are safe to publish.

## 5. Alternatives considered

* **Keep `InvalidArgumentError` and add more controller conditions.** Rejected: the base type would
  continue to erase the semantic distinction that the conditions need.
* **Create one base class per HTTP status.** Rejected: transport policy would become a domain dependency
  and would not transfer cleanly to non-HTTP entry points.
* **Store `httpStatus` on each error.** Rejected: it duplicates the mapping implied by `kind` and lets
  concrete domain errors choose transport behavior.
* **Classify failures by the directory that throws them.** Rejected: location does not distinguish a
  caller outcome, a managed dependency failure, and an impossible state.
* **Make the relational journal inherit from the in-memory journal.** Rejected: the adapters have
  different storage mechanics and need only the same interface and translated failure contract.
* **Wait to define infrastructure failures until a database exists.** Rejected: defining and testing
  the boundary now makes the future adapter swap explicit without manufacturing in-memory failures.
* **Permit bare errors and rely on review.** Rejected: the current mixture demonstrates that review
  alone does not preserve a closed error taxonomy.

## 6. Limits accepted

This decision does not add a relational database adapter, retry policy, correlation identifier,
central logging system, or monitoring policy. It defines enough structure for those concerns to
distinguish expected outcomes, managed technical failures, and defects later.

It does not turn every third-party exception into an infrastructure error. Adapters translate only
failures they understand and can characterize. Everything else remains an unrecognized opaque 500.

It does not decide whether stable codes become part of the public HTTP response. That belongs with an
explicit endpoint contract. It also does not expose metadata by default or standardize user-facing
localization.

## 7. Conclusion

Ships and Cargo will use one typed error kernel with mandatory domain ownership and separate domain,
infrastructure, and invariant categories. The application boundary, rather than concrete errors,
will map those semantics to HTTP behavior. This creates a stable contract for current code and future
persistence adapters, but it does not provide a database, retry strategy, or complete observability
system.
