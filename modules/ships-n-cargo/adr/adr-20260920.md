# ADR: Adopt toolchain ESM semantics without choosing a production runtime

**Date:** 2026-09-20

## 1. Context

Ships and Cargo is a proof of concept that supports Node.js 24 for development and continuous integration. TypeScript is checked with `tsc --noEmit`, and Vitest transforms and executes the TypeScript source. The project does not publish a package, create a deployable JavaScript directory, or run the application as a production service.

The package currently declares CommonJS through its TypeScript compiler settings. Its active test toolchain is ESM-oriented, and the Vitest configuration already uses the explicit `.mjs` extension.

## 2. Problem

**The module declaration no longer describes the active toolchain.** CommonJS remains configured even though no CommonJS output is emitted and Vitest executes the source through Vite's module pipeline.

**Choosing Node-native ESM would prematurely choose a runtime contract.** Strict Node ESM resolution would require explicit extensions throughout the relative import graph. That work would optimize the source for direct Node execution even though the proof of concept has no production runtime.

**A future runtime decision must remain open.** Direct Node TypeScript execution, Bun, a separate build configuration, or another packaging tool may impose different module-resolution requirements.

## 3. Decision

### The package declares ESM semantics

The package will declare `"type": "module"`. JavaScript configuration files and tooling will therefore use ESM semantics by default. Explicit `.mjs` files may retain that extension when it makes their role clear and avoids a rename with no behavioral benefit.

### TypeScript follows the active toolchain

TypeScript will preserve ESM source syntax and use bundler-style module resolution for type-checking. Relative TypeScript imports may remain extensionless because Vite and Vitest, rather than Node's native module loader, resolve and execute them.

### The project continues to type-check without emitting JavaScript

This decision does not restore a compilation artifact. `tsc --noEmit` remains the TypeScript gate, and Vitest remains the source executor for tests.

### Runtime-specific module rules are deferred

The project will adopt Node-native extension rules only if direct Node execution becomes a requirement. A Bun runtime, build output, or published package will likewise require a separate decision based on an actual delivery target.

## 4. Consequences

The checked-in module declaration will match the ESM-oriented development toolchain, and CommonJS-specific configuration will no longer be necessary.

**The source will not be directly executable by Node's strict ESM loader.** Extensionless relative imports remain a toolchain convention, not a claim of Node-native compatibility.

**Changing the runtime later may require broad import edits.** Deferring that work avoids paying the cost before the target runtime is known.

## 5. Alternatives considered

* **Keep CommonJS semantics.** Rejected: no CommonJS artifact is emitted, so the setting describes an output and runtime contract the project does not use.
* **Adopt Node-native ESM resolution now.** Deferred. It becomes worthwhile when direct Node execution or a Node-targeted distributable is required.
* **Run TypeScript directly with Node.js.** Deferred. Native type stripping does not type-check and does not support every TypeScript construct used by the project without additional transformation choices.
* **Adopt Bun as the runtime.** Deferred. The proof of concept has no production runtime requirement from which to evaluate that choice.
* **Add a separate production build configuration.** Deferred. A `tsconfig.build.json` is useful only when the project needs a deployable JavaScript artifact.

## 6. Limits accepted

This decision does not select a production runtime, make the application directly executable from TypeScript, produce a `dist/` directory, or define package-publication behavior. It aligns development-time module semantics only.

It also does not prove that a future Node, Bun, or bundled deployment will accept the current import graph unchanged.

## 7. Conclusion

Ships and Cargo will declare ESM and use bundler-style TypeScript module resolution because those semantics match the active no-emit Vitest toolchain. This alignment deliberately does not choose how the proof of concept will eventually run or ship.
