# ADR: Add a transactionally positioned feed for durable read-side projections

**Date:** 2026-10-12

## 1. Context

Ships and Cargo stores each aggregate's events in an event journal. The journal identifies an
event within one aggregate by `(aggregate_id, version)`, and appends use the expected stream
version for optimistic concurrency. [ADR-20260921-2](adr-20260921-2.md) retained that composite
stream position as journal row identity and explicitly deferred global ordering and projection
delivery.

The current ship-history projection reads one aggregate stream and builds its response on demand.
This is appropriate for answering what happened to one ship, but it is not a durable CQRS read
model. Answering questions such as which ships are at sea or which ships are at a port would require
discovering and replaying many aggregate streams for every request.

The journal now has in-memory, PostgreSQL, and SQLite adapters. PostgreSQL and SQLite append events
inside database transactions, while the in-memory adapter completes an append synchronously. The
canonical event payload already carries `occurredAt` and `recordedAt`; neither timestamp establishes
a safe cross-stream consumption order.

## 2. Problem

**There is no resumable feed across aggregate streams.** Stream versions order events for one ship,
but a projector cannot ask for the next stored events after its last completed work.

**A timestamp or UUID is not a transaction checkpoint.** Generation order can differ from commit
order when transactions overlap. Advancing a projector past a later committed value could cause it
to miss an earlier value that becomes visible afterward.

**The read side has no durable progress or recovery boundary.** There is no checkpoint from which a
projector can resume after shutdown, no atomic relationship between projected state and progress,
and no repeatable way to rebuild a read model from the journal.

**Premature generalization would obscure the behavior being explored.** One concrete read model is
not enough evidence for a generic projection framework, partitioning model, or distributed lease
protocol.

## 3. Decision

### Every stored event receives a transactional global position

Each journal adapter will assign every successfully stored event an immutable numeric global
position. The global position is distinct from the aggregate stream version and the payload's
schema version. A multi-event append receives consecutive positions in the same order as its
events. An append that fails consumes no positions.

PostgreSQL will keep the next position in a counter row. An append will lock that row, assign and
advance the required positions, insert the events, and commit those changes in one transaction.
Position allocation will occur near the end of the append transaction so the global lock is held
only for the journal write. This deliberately serializes successful position allocation across
aggregate streams.

SQLite will assign positions inside its existing `BEGIN IMMEDIATE` append transaction. Its
single-writer behavior already serializes allocation. The in-memory adapter will update its
aggregate stream, global feed, and next position as one synchronous state change.

The relational schema will not duplicate `recordedAt`. The canonical payload remains the source of
event timestamps, while global position alone provides feed traversal order. UUIDv7 event identity
also remains deferred until a concrete consumer requires stable identity or deduplication beyond
the existing aggregate stream position.

### The journal exposes a read-only global event feed

A read capability will return stored events after an opaque position in ascending order, subject to
a bounded batch size. Each feed entry will expose its global position, aggregate ID, stream version,
and deserialized domain event. The feed will also expose its current head position so projection lag
and catch-up can be observed.

Application code will not perform arithmetic on positions or give them domain meaning. Persistent
adapters will store them as 64-bit integers, and TypeScript boundaries will preserve their full
integer precision.

### One concrete ship overview is materialized asynchronously

The first durable read model will summarize the current state needed to find and display ships
without rebuilding aggregates. It will support looking up a ship by ID and listing ships by status
or current port. Its shape will be driven by those queries rather than by the aggregate's internal
representation.

The existing ship-history endpoint will remain journal-backed because it answers a historical
question. The ship overview will answer current-state queries from materialized data. A successful
command commits its events before the projector catches up, so overview queries are explicitly
eventually consistent.

### Projected state and progress change atomically

The ship-overview projector will own a durable checkpoint. For each bounded batch, it will lock its
checkpoint row, read from the position stored there, update the ship-overview rows, and advance the
checkpoint in one transaction. A rollback leaves both the view and checkpoint unchanged, allowing
the batch to be retried.

Checkpoint-row locking will also coordinate multiple application instances. Only the instance that
holds the row lock can apply the next batch. Locks are released automatically at transaction end or
connection failure, so this design does not require a separate leader lease for the first
projection.

The in-memory runtime will preserve the same observable contract with ephemeral overview and
checkpoint state. Its journal, view, and checkpoint all reset together on restart.

### Projection lifecycle follows the application lifecycle

The application runtime will start the ship-overview projector, let it catch up in bounded batches,
and stop it during graceful shutdown before closing its database resources. Projection failure will
be visible and retryable without changing committed journal events.

An operator command will clear the ship overview and its checkpoint, then replay the complete feed.
Rebuild will use the same event handlers as normal catch-up so a projection can be replaced without
rewriting journal history.

### No generic projection framework is introduced

The implementation will contain one ship-overview projector and only the infrastructure it needs.
Shared projection abstractions, partitioned processing, and reusable handler registries will be
extracted only after another real projection demonstrates the same requirements.

## 4. Consequences

The application gains a durable query model that can resume, report lag, and rebuild from the event
journal. Queries no longer need to discover and replay aggregate streams. All adapters share one
feed contract while retaining their storage-specific transaction mechanisms.

**Every successful append briefly contends on one PostgreSQL counter row.** This is a deliberate
correctness and simplicity tradeoff. Append latency and lock waits must be measured before replacing
it with a more concurrent allocation scheme.

**Overview queries can temporarily return stale state.** Clients and tests must not assume that a
successful command makes the asynchronous read model current immediately. Catch-up status provides
an explicit way to observe that boundary.

**Projection batches become database transactions.** Batch size must remain bounded so checkpoint
locks, transaction duration, and retry cost remain controlled.

The event journal remains the source of truth. The ship overview is disposable derived state, and
its tables may be cleared and rebuilt without changing domain history.

## 5. Alternatives considered

* **Use UUIDv7 as the feed cursor.** Rejected: UUID generation order is not transaction commit order,
  so a later visible UUID could be checkpointed before an earlier transaction commits.
* **Use event timestamps as the feed cursor.** Rejected: timestamps can collide, clocks can move,
  and the payload's times do not provide a transaction visibility boundary.
* **Use a PostgreSQL sequence with a high-water monitor.** Deferred. It permits greater append
  concurrency but requires detecting unresolved and permanently abandoned gaps. It becomes
  worthwhile if measured counter contention justifies that operational complexity.
* **Update the ship overview inline with every command.** Rejected: it would couple command success
  to one derived view and would not exercise resumable asynchronous projection or rebuild behavior.
* **Build a generic projection engine first.** Rejected: one projection cannot establish which
  lifecycle, dispatch, retry, partitioning, and monitoring abstractions are genuinely shared.
* **Run one manually designated projector instance.** Rejected: checkpoint-row locking provides
  automatic crash release and safe coordination when several application instances start.

## 6. Limits accepted

This decision does not publish events outside the application, add a transactional outbox, or
promise exactly-once processing across separate systems. It does not add snapshots, sagas,
partitioned projection work, or multi-region ordering.

The counter provides a traversal order, not a business chronology across ships. Business decisions
continue to depend only on each aggregate's ordered stream.

Checkpoint-row locking serializes one projection's batches. It does not distribute a projection
across workers or make slow handlers faster. Those capabilities require demonstrated throughput
needs and a separate decision.

## 7. Conclusion

Ships and Cargo will add a transactionally allocated numeric position to every stored event and use
that feed to maintain one durable, eventually consistent ship-overview projection. Projected state
and its checkpoint will advance atomically, restart and rebuild will replay the same handlers, and
the implementation will remain concrete until another projection reveals a useful shared design.
