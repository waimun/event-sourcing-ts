# ADR: Configure portable error architecture enforcement with explicit source scopes

**Date:** 2026-10-17

## 1. Context

The typed error kernel established by [ADR-20260920-2](adr-20260920-2.md) requires every
intentionally modeled production failure to belong to `BaseError`. A TypeScript-aware analyzer in
`scripts/error-architecture.ts` enforces that production throw statements use the configured
kernel and that native `Error` subclasses do not form a separate hierarchy. The lint gate invokes
that analyzer through `scripts/check-error-architecture.ts`.

The analyzer already accepts a TypeScript configuration, a source root, and an error-kernel file.
The launcher does not expose that flexibility. It hard-codes one `src` source root and one
`src/shared/errors/kernel.ts` kernel. That matches the current Ships and Cargo layout, but a
repository containing multiple bounded contexts needs one source root and one kernel per context.

The policy boundary is production code inside an explicitly governed bounded context. Tests,
fixtures, and repository-level infrastructure outside those configured contexts are not governed
by this rule.

## 2. Problem

**Repository layout is embedded in executable policy.** A launcher that assumes `src` cannot run
unchanged in a repository whose bounded contexts live below `modules`. Editing the launcher for
each layout makes operational wiring and policy logic difficult to distinguish.

**Independent launchers can drift.** If each repository owns a structurally different loop,
formatter, exit-code policy, or failure behavior, identical analyzer code does not provide
identical compliance. A repository may appear protected while invoking only part of its intended
scope.

**Automatic discovery cannot prove the policy boundary.** Searching for files named
`shared/errors/kernel.ts` can find conventional contexts, but it cannot determine whether a missing
kernel means an intentionally excluded directory or an accidentally ungoverned bounded context.
Silent discovery is therefore weaker than an explicit reviewed list.

**A repository root cannot use one bounded context's kernel as a universal ancestor.** Separate
bounded contexts own separate `BaseError` identities. Analyzing several contexts against one
kernel would report the other legitimate kernels as foreign native-error hierarchies.

## 3. Decision

### Each repository declares its governed source scopes explicitly

Each repository will provide `scripts/error-architecture.config.ts`. It will declare the
repository TypeScript configuration and an ordered, non-empty list of scopes. Every scope contains
a stable display name, its production source root, and the `BaseError` kernel governing that root.
Paths are repository-relative and are resolved from the current project root.

Ships and Cargo will declare one scope for `src` and `src/shared/errors/kernel.ts`. A repository
with multiple bounded contexts will declare one scope per context. Directories absent from the list
are outside this policy, including repository-level infrastructure when that exclusion is
intentional.

The launcher will fail rather than pass when configuration contains no scopes, a configured kernel
cannot be loaded, or the TypeScript project cannot be loaded. Configuration remains the reviewed
source of truth; the launcher will not infer additional scopes from the filesystem.

### One layout-neutral launcher enforces every configured scope

`scripts/check-error-architecture.ts` will contain no repository-specific source paths. It will
load the configuration, invoke the analyzer once per scope, prefix every formatted diagnostic with
the scope name, aggregate the diagnostics deterministically, and set a failing exit code when any
scope reports a violation.

The launcher behavior and source will be reusable byte for byte across repositories. Only
`scripts/error-architecture.config.ts` may vary to express layout and policy boundaries.

### The analyzer and its contract tests remain common artifacts

`scripts/error-architecture.ts`, `scripts/check-error-architecture.ts`, and their contract tests
will be reusable without repository-specific branches. Tests will prove both a single `src` scope
and multiple independently governed scopes, including unambiguous scope-prefixed diagnostics and
aggregate failure behavior.

This change preserves the analyzer's current definition of production files, native subclasses,
throw compatibility, and direct caught-value rethrows. Portability must not silently change which
source constructs the policy accepts.

### Lint remains the enforcement entry point

Each adopting repository will run the common launcher from its lint command. A successful lint run
means every explicitly configured scope produced no diagnostics. Adoption is incomplete if the
repository merely carries the analyzer without invoking the launcher from its verification path.

## 4. Consequences

A one-context repository and a multiple-context repository can execute the same policy machinery
while naming different source layouts in configuration. Each bounded context is checked against
its own error identity, and diagnostic paths remain understandable because the launcher supplies
the scope name.

Adding a bounded context now requires an explicit configuration change. This makes policy coverage
reviewable, but it also means reviewers must notice a new context that was not added to the list.

**The common artifacts are copied between repositories until they are packaged.** During this
period, a policy change must update both copies and prove that their common files remain identical.
The explicit configuration isolates legitimate differences but does not automate synchronization.

**Every configured scope creates another TypeScript analysis pass.** This favors simple,
independent invocation over an optimized shared program. The expected number of bounded contexts
is small, so clarity is preferred until measured runtime justifies a more complex API.

## 5. Alternatives considered

* **Keep a repository-specific launcher.** Rejected: layout changes would remain mixed with exit
  behavior and diagnostic aggregation, allowing compliance wiring to drift.
* **Discover kernels and source roots automatically.** Rejected: conventions cannot distinguish an
  intentional exclusion from a missing policy declaration, so a new context could be skipped
  silently.
* **Analyze the repository once against one kernel.** Rejected: separately owned `BaseError`
  hierarchies are not interchangeable ancestors and would create false violations.
* **Pass every scope through package-script command-line arguments.** Rejected: long command lines
  are harder to review, type-check, and reuse than a named configuration artifact.
* **Publish the checker as an internal package now.** Deferred. Packaging becomes worthwhile when a
  third consumer or repeated synchronization work outweighs the release and versioning overhead.

## 6. Limits accepted

This decision does not strengthen the analyzer's treatment of `any`, structurally compatible
objects, class expressions, kernel-local subclasses, nested rethrows, promise rejections, or
exceptions thrown implicitly by dependencies. Those are policy changes and require separate
decisions and regression tests.

Explicit configuration cannot detect a bounded context that was never listed. Repository review
and tests can prove declared scopes, not infer organizational intent.

The launcher does not make repository-level infrastructure comply when that directory is outside
the configured scopes. It also does not merge separate bounded-context kernels into a shared runtime
identity.

The initial copied artifacts do not provide automatic downstream updates. Byte-for-byte comparison
can demonstrate portability at adoption time, but later changes still require deliberate
synchronization until packaging is justified.

## 7. Conclusion

Error architecture enforcement will separate common policy execution from repository layout. One
analyzer, launcher, and contract-test suite will operate over an explicit list of independently
governed source scopes, while a small repository configuration records the only intended layout
difference. This makes the current enforcement portable and reviewable, but it does not strengthen
the analyzer, discover organizational boundaries, or automate distribution of future updates.
